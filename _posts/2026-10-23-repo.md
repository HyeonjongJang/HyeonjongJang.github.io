*An ESP32-S3 board gives a vision-language model eyes and hands on a real iPhone: no Mac at runtime, no jailbreak, no developer account.*

## What it is

ESP32 iPhone Agent is an open-source project that turns a ~$7 ESP32-S3 microcontroller into a bridge between a vision-capable AI model and a physical iPhone. The board plugs into the phone's USB-C port and does two things: it acts as an AirPlay receiver so the model can see the screen, and it acts as a USB HID mouse and keyboard so the model can tap, swipe, and type. An accompanying iOS app running on the same phone decodes the mirrored video, sends screenshots to any OpenAI-compatible vision endpoint, and translates the model's decisions into HID commands back through the board.

The target audience is developers experimenting with AI agents that interact with real phone interfaces: the "computer use" pattern applied to iOS, without requiring a Mac tethered at runtime, jailbreaking, or a paid developer account (a free Apple ID can sign the app, with a 7-day re-signing cycle). The project requires iOS 18 or later.

## How it works

The system has three parts (eyes, hands, and brain) connected in a loop.

**Eyes: AirPlay mirroring to the board.** The ESP32-S3 creates its own Wi-Fi hotspot and advertises itself as an AirPlay receiver called "ESP32 Agent" in the phone's Screen Mirroring menu. When the phone mirrors to it, the board receives an H.264 video stream. It does not decode the video itself: it passes the compressed stream over BLE to the iOS app running on the same phone. The phone keeps using cellular data for internet access while its Wi-Fi is connected to the board's hotspot.

**Hands: USB HID.** Physically plugged into the phone's USB-C port, the board presents itself as a standard USB mouse and keyboard. With iOS's AssistiveTouch turned on, the mouse controls an on-screen pointer: a click becomes a tap, a drag becomes a swipe, and keyboard events become text input (ASCII only at this time).

**Brain: the iOS app.** The app decodes the H.264 stream, captures screenshots, and sends them to whatever OpenAI-compatible vision model endpoint the user has configured. It runs a planner–actor loop: the planner decides what to do next, the actor executes it: tap, swipe, draw, type, press keys, go home, or finish. While working, the app moves to the background and shows progress through the Dynamic Island.

**Closing the loop: pointer tracking and correction.** Because the USB HID pointer uses relative positioning, the app needs to know where it actually is. The README describes a specific correction mechanism: before precise taps, the app wiggles the pointer, finds it in the mirrored screenshot, and corrects any drift. After each action, the app waits for the screen to settle and tells the model whether anything changed. If the board, hotspot, or mirroring connection drops, the run pauses and resumes from the same step when reconnected.

Think of it like a remote-controlled camera and robot arm bolted to the outside of a locked room (my analogy, not the project's). The camera peers through the window (AirPlay mirror), the arm reaches in through a slot in the door (USB HID), and a person in another building watches the camera feed and radios instructions to the arm. The room itself (iOS) is untouched: no jailbreak, no debug hooks, no accessibility APIs beyond the standard AssistiveTouch.

**Review and export.** Every run is saved on the phone and can be replayed step by step with taps and swipes drawn on top. Screenshots, actions, and annotations can be exported from the app for analysis.

## Using it

The README describes a three-stage setup: flash the board, build the app, and configure.

**Flash the board** (requires a Mac with the board plugged in via USB):

arduino-cli lib install "NimBLE-Arduino@2.5.1"
hardware/flash.sh            # optional: [serial port] [--debug]

The README notes you need [arduino-cli](https://arduino.github.io/arduino-cli/), the ESP32 core 3.3.x, and NimBLE-Arduino 2.5.x. It emphasizes always building with `flash.sh` because the script applies BLE buffer sizes defined in `hardware/hid_bridge/nimble_cfg.h`.

**Build and install the iOS app** (requires Xcode on a Mac):

cp ios/Config/Local.xcconfig.example ios/Config/Local.xcconfig   # set DEVELOPMENT_TEAM and IA_BUNDLE_ID
open ios/IPhoneAgent.xcodeproj                                    # run the IPhoneAgent scheme on your iPhone

The Xcode project is generated with XcodeGen from `ios/project.yml`. A free Apple ID can sign it, though re-signing is required every 7 days. The one-tap hotspot join feature requires a paid Apple developer account; without one, the app shows the hotspot password for manual joining.

**First-time setup in the app** walks through four steps: pair the board over Bluetooth, join the board's Wi-Fi and start Screen Mirroring, turn on AssistiveTouch for pointer calibration, and enter a model endpoint and API key.

**Running a task:** type a goal (the README gives the example *"Open Settings and go to Wi-Fi"*) and press Start. The agent can also be triggered through Siri, Shortcuts, widgets, or Control Center for saved tasks.

I have not built or run this project: the steps above are taken directly from the README. The Mac is only needed for the initial flash and app build; at runtime, the system is just the phone and the board.

## Notable details

**Model flexibility.** The app works with any OpenAI-compatible vision endpoint: the README lists vLLM, SGLang, llama.cpp, Ollama, and cloud APIs. Users can set separate models for the planner and actor roles. The app queries the endpoint's model list for selection. The project was developed using nvidia/Qwen3.8-Flash-Next-NVFP4 served on two DGX Sparks.

**Bandwidth constraints.** BLE carries roughly 300–500 kbps according to the README, so the mirrored screen runs at 480×1040 resolution at up to 5 fps. Each step takes a few seconds, with most of the time spent on model inference.

**iOS mirroring limits.** iOS does not mirror certain screens (passcode entry, Apple Pay, and DRM-protected video), so the agent cannot see or interact with those. Mirroring stops when the phone locks.

**Connectivity trade-off.** While the agent runs, the phone's Wi-Fi is occupied by the board's hotspot (no internet over Wi-Fi); the model must be reached over cellular data.

**Keyboard limitation.** Text input is ASCII only. Landscape apps are not yet supported: coordinate mapping and calibration currently assume portrait orientation.

**Legacy version.** The current version is self-contained (phone + board). An earlier version required a Mac or Linux computer running UxPlay and a Python server; it is preserved as tag `v0.1.0` and the `legacy` branch.

**License.** The project is MIT-licensed, except for the AirPlay receiver code in `hardware/hid_bridge/src/airplay/`, which is ported from UxPlay and is GPL-3.0. The firmware binary that links it is therefore distributed under GPL-3.0.

**Maturity.** The repo is written primarily in C (firmware) and Swift (iOS app), with 3,564 stars at the time of writing. CI is active. The roadmap lists landscape support, non-ASCII input, multi-action steps, and a curated model compatibility list as open items.

**Responsible use note.** The README states: only automate devices and accounts you own or are allowed to use, respect the terms of the apps involved, and keep the stop button within reach.

## Why it matters

Most "computer use" agent demos target desktop browsers or Android (where accessibility APIs are more open). iOS has been harder to instrument without jailbreaking or tethering to a Mac with developer tools. This project sidesteps the software restrictions entirely by working at the hardware layer: AirPlay and USB HID are standard iOS features that require no special permissions. **In my view, this is the most practical path to iOS computer-use agents today: it trades bandwidth and resolution for zero dependence on Apple's developer toolchain at runtime, which is a constraint many agent researchers will accept.**

The related-projects table in the README gives useful context: VersaiOS needs a computer, actell needs Developer Mode, AidenAI targets Android with HDMI capture, and boboabw/phone-agent is the closest approach but lacks the AirPlay "eyes." WebDriverAgent-based tools like mobile-mcp and Midscene require a Mac and code signing.
